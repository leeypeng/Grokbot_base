# 网络故障证据整理

## R — 原文依据
来源：`docs/a123/rst-syscall.md` 的开头与“小插曲”。[原文](https://github.com/hoochanlon/fq-book/blob/master/docs/a123/rst-syscall.md)。短引文：“多方面考虑原因（多种可能）”。仅继承多假设比较和应用请求验证，不继承其将错误共同归因 hosts 的断言。

## I — 方法解释
先把观察与解释分开。
记录发生时间、目标域名、应用和完整错误。
按同一目标比较 ICMP 与实际 HTTP/TLS 请求结果。
列出代理入口、解析及服务端等候选因素，并给出各自需要的证据。
每次只改变一个可回滚变量，用原请求复测，不以症状名称宣布根因。

## A1 — 案例
原书案例：作者发现 GitHub ping 不通但网页可访问，遂改用 curl；ICMP 过滤是其推测，未被独立证明。合成演练：ping 成功而 HTTPS 重置，只能输出“ICMP响应存在、HTTPS失败”，不能写“DNS已坏”。

## A2 — 适用与区分
用于“连接重置”“浏览器能开而终端失败”“ping结果与网页矛盾”等证据不足问题。若已确认应用指向停止的本地代理，转代理入口卡；若双入口冲突，转代理链卡。不处理SSH/WireGuard完整部署。

## E — 执行契约
输入：目标、系统/应用版本、完整错误、当前代理路径与已做测试。输出表列“观察、假设、支持证据、反证、下一步”。缺输入时只询问最关键缺项并列可收集日志；有对照结果则更新假设，不将相关性当因果。任何配置试改先记录原值和恢复方法。完成条件：用户可按下一步取得可判别结果，已确认与未确认明确分开；未实测不得写恢复成功。

## B — 边界
仅是证据整理，不是穷尽DNS/TCP/TLS故障的诊断器。原文含旧机制解释，当前客户端语义须查官方文档。不能仅凭超时、RST、403或SSL_ERR_SYSCALL判定封锁、污染或认证要求；不关闭证书校验来“验证”。
