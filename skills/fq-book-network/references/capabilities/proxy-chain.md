# 双代理端口与前置关系核对

## R — 原文依据
来源：`docs/append/ss-relay.md` 第一至第四步，转载作者夏天。[原文](https://github.com/hoochanlon/fq-book/blob/master/docs/append/ss-relay.md)。短引文：“此时会提醒你端口被占用”。原例两个本地客户端均用1080，第二个改1081；数字仅属于案例。

## I — 方法解释
先为每个客户端标明“前置”或“目标”角色。
列出每个进程的监听协议、地址、端口，不只比较端口数字。
核查应用入口指向目标客户端，目标客户端的前置字段指向前置客户端入口。
把逻辑转发依赖与实际远端连接顺序分开画图。
先解除已证实冲突，再逐段验证，最后测原目标，不承诺加跳必然提速。

## A1 — 案例
原书转述例：维也纳节点作为前置、英国节点作为目标，两个客户端本地入口冲突后调整第二入口并配置前置。作者提供最终测试截图，但本次未查看，不能宣称实测速率。合成演练：A与B都要求127.0.0.1:1080/TCP，先查占用进程；1081仅是待验证候选，不能称已空闲。

## A2 — 适用与区分
用于双客户端端口冲突、前置跳序混淆、换入口后应用仍走旧代理等问题。单客户端停止后的残留走代理入口卡；链已核对但目标仍失败，走证据整理卡。此卡不生成厂商专有配置，不替代上游当前文档。

## E — 执行契约
输入：两客户端版本、监听端点、前置字段、应用入口及目标节点。输出角色表与路径：应用→目标客户端本地入口→前置客户端本地入口→前置远端→目标远端→目的服务，并按实现标未知项。缺关键字段先补齐；同一地址/协议/端口冲突证实后，才提出备用端口。改动前备份双方配置和应用入口、写回滚方法；每次只改一项并复测。完成条件：入口唯一、角色清楚、所有连线有配置证据；未运行测试仅报“配置审阅通过”。

## B — 边界
没有实际监听证据，不把相同数字必定认作冲突；不同地址/协议可能不同。增加中转不保证更快。源文图片未核验，当前客户端字段可能不同。严禁把环回监听顺手改成公开监听，或在缺凭据/权限时自设远端。
